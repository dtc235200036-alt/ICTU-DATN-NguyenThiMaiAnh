<decisions>
## Implementation Decisions

### Repo layout & tooling
- **D-01:** Monorepo at repo root: `backend/` (FastAPI Web API), `frontend/` (React), `ai-service/` (created in Phase 4; only a stub client lives in backend now), `deploy/` (docker-compose, Apache config, certs script). Docs stay in `docs/`. [auto] Q: "Repo layout?" → Selected: "monorepo backend/frontend/ai-service/deploy" (recommended)
- **D-02:** Python 3.12 managed with `uv` (`backend/pyproject.toml`, `uv.lock`); Node 20 (nvm, already installed) + Vite for the client; pnpm or npm — Developer's Discretion.
- **D-03:** Backend stack per research STACK.md: FastAPI, SQLAlchemy 2.0 **sync** + PyMySQL, Alembic migrations, Pydantic v2, PyJWT, bcrypt. Tests with pytest against a real MySQL (docker) — keep tests few and focused on RBAC/ownership + concurrency invariants (user preference: fewer tests).

### Database
- **D-04:** MySQL 8 in Docker; schema `thesis_core` with `utf8mb4` + `utf8mb4_vietnamese_ci`; tables/columns follow `docs/chuong-3-thiet-ke/02-thiet-ke-csdl.md` (19-table ERD) — Phase 2 migrates only tables needed now (users/accounts, roles, cohorts/đợt, topics/de_tai, topic registration, supervisor assignment, similarity result for title check, thresholds as needed) but names must match the ERD exactly so later phases extend, not rename. — **Reversibility:** costly — renaming tables later touches migrations + all queries
- **D-05:** 1 SV : 1 active topic and 1 topic : 1 SV enforced by **DB unique constraints + transactional check** (not only app code) so concurrent registrations cannot both succeed (success criterion 4).
- **D-06:** Unicode NFC normalization at the API boundary for all text inputs (Pydantic validator).

### Auth & RBAC
- **D-07:** Login by mã SV/GV or email + password → short-lived access JWT (Bearer, `Authorization` header, per architecture §3.3.4) + refresh token; client keeps session across reload (refresh token in httpOnly cookie; access token in memory). [auto] Q: "Session storage?" → Selected: "httpOnly refresh cookie + in-memory access token" (recommended — XSS-safer than localStorage, still survives reload)
- **D-08:** 3 roles SINH_VIEN / GIANG_VIEN / BO_MON enforced with FastAPI dependencies on every route + ownership checks in the service layer; locked accounts cannot log in or refresh.

### Frontend
- **D-09:** React + Vite + TypeScript + Ant Design v5 + TanStack Query + React Router; screens follow mockups `docs/chuong-3-thiet-ke/mockup/mh-01..mh-07` (login, 3 dashboards, topic list/propose/register, approve & assign). Vietnamese UI text.
- **D-10:** Title-duplicate warning on propose/register calls backend → **AI stub client** returning deterministic fake matches (interface identical to `/check-title` contract in §3.3.5) until Phase 4.

### Deployment (DEPL-02)
- **D-11:** Local-first deployment with **Docker Compose**: `mysql`, `api` (uvicorn), and `apache` (httpd 2.4, `mod_proxy_http`, `mod_ssl`) serving the built React app statically and proxying `/api` → api. TLS via a self-signed certificate generated by a `deploy/` script (mkcert if available). AI service will be added in Phase 4 with no Apache route. Moving to a real server (e.g. box 10.22.7.144) is a Phase 5 concern — compose must be portable. — **Reversibility:** reversible
- **D-12:** Apache config sets `LimitRequestBody` ≥ 20MB and proxy timeouts ≥ 60s now (research pitfall: discover upload/timeout issues early).

### Seed data (DATA-01)
- **D-13:** Idempotent seed script (Faker `vi_VN`, fixed random seed) creating 100 SV, 30 GV, 1 Bộ môn admin account, at least one open cohort/đợt; demo credentials documented in `deploy/README` (dev-only password).

### Developer's Discretion

- Which Phase-2-only ERD tables to create first, as long as names match the ERD.
