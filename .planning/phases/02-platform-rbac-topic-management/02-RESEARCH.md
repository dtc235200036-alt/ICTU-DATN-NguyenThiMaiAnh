## Summary

Phase 2 is the first working vertical slice of a 3-component SOA thesis-management system (Web API, React client, and a **stubbed** AI service). The stack is already locked by CONTEXT.md D-03/D-09: FastAPI + SQLAlchemy 2.0 **sync** + PyMySQL + Alembic against MySQL 8 (`thesis_core` schema only), JWT auth (Bearer access token + httpOnly-cookie refresh token), and a React + Vite + TypeScript + Ant Design v5 + TanStack Query + React Router client, all served behind an `httpd:2.4` reverse proxy with a self-signed TLS cert. This research verifies every recommended package still exists and is current on its registry, quotes the exact ERD columns/state machine/API contracts Phase 2 must match (from Phase 1's completed design docs), and surfaces the pitfalls specific to this exact combination: Vietnamese-collation MySQL setup, NFC normalization at the API boundary, the two required concurrency mechanisms for topic registration (a generated-column unique index + a conditional `UPDATE`/`SELECT...FOR UPDATE`), RBAC-as-a-shared-dependency (not per-route ad hoc checks), and Apache/FastAPI proxy-header/timeout/SPA-fallback configuration that must be stood up now rather than deferred.

Nothing in this phase touches the real AI service, document upload, or file parsing (all Phase 3/4). The only AI-shaped work is a Python stub object matching the `/check-title` response shape (`{matches: [{ref_id, ty_le}], ...}`) called from the topic-proposal service — no HTTP call, no `httpx` dependency required yet.

**Primary recommendation:** Build `backend/` as a single FastAPI app with sync SQLAlchemy 2.0 + PyMySQL against `mysql+pymysql://`, one Alembic revision chain for `thesis_core`, a single reusable `require_role(*roles)` + ownership-check FastAPI dependency applied to every router from the very first endpoint, and stand up the `httpd:2.4` reverse-proxy container in week 1 (not at the end) so upload-size/timeout/proxy-header issues surface early per Pitfall 10.

## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| Login / JWT issuance / password verification | API / Backend | — | FastAPI validates credentials against `thesis_core.tai_khoan`, issues signed JWT; no client-side auth logic beyond storing tokens |
| Session persistence across reload | Browser / Client | API / Backend | Access token held in memory (lost on reload) is re-minted via the httpOnly refresh cookie automatically sent to `/api/auth/refresh` — browser owns "hold in memory + retry on 401", API owns "validate refresh cookie, mint new access token" |
| Role + ownership authorization | API / Backend | — | NFR-04 explicitly requires server-side enforcement on every endpoint; UI hiding buttons is cosmetic only, never authoritative (Pitfall 9) |
| Account management (Bộ môn CRUD SV/GV) | API / Backend | Database / Storage | Business rules (unique mã SV/GV, lock semantics) enforced in service layer + DB unique constraints |
| Cohort (đợt đồ án) open/close | API / Backend | Database / Storage | `dot_do_an.trang_thai` gates topic-proposal/registration endpoints (UC0.3, UC1.1-E1) |
| Topic proposal / registration / approval workflow | API / Backend | Database / Storage | State machine transitions (`NHAP→CHO_DUYET→DA_DUYET/TU_CHOI→DA_PHAN_CONG`) are server-authoritative; DB enforces the two uniqueness invariants |
| Topic list/filter rendering | Browser / Client | API / Backend | API returns role-scoped, paginated JSON (NFR-12: P95 ≤ 1s); client only renders + manages filter UI state |
| Concurrent topic-registration exclusion (1 SV:1 topic, 1 topic:1 SV) | Database / Storage | API / Backend | Generated column + UNIQUE index and conditional `UPDATE ... WHERE sinh_vien_id IS NULL` — the invariant is unenforceable by application code alone under real concurrency (§3.2.5) |
| AI title-duplicate check (Phase 2 = stub only) | API / Backend | — | A Python object with the same call signature as the future `ai_client`, no network call in Phase 2; real AI Service tier arrives in Phase 4 |
| Static asset hosting + TLS termination + `/api` proxy | CDN / Static (Apache) | — | Apache serves the Vite build from `DocumentRoot` and reverse-proxies only `/api/*`; matches §3.3.1/§3.3.3 SOA boundary (AI service gets no route at all) |
| Seed data generation | Database / Storage | API / Backend | Idempotent script writes directly via the same SQLAlchemy models/session used by the app, not raw SQL, so it stays in sync with schema changes |

### Pattern 1: Shared `require_role` + ownership dependency, applied from the first endpoint

**What:** A single reusable FastAPI dependency factory checks the JWT's `vai_tro` claim against an allow-list, and a second per-resource dependency loads the target row and checks ownership (e.g., "is this GVHD's `giang_vien_id` == `de_tai.giang_vien_id`?").
**When to use:** Every protected route, starting with the very first one built in Phase 2 (per PITFALLS.md Pitfall 9: retrofitting authorization later is the highest-recovery-cost mistake in this domain).
**Example:**
```python
# backend/app/core/deps.py
from fastapi import Depends, HTTPException, status
from app.core.security import decode_access_token

def require_role(*roles: str):
    def _dep(token_payload: dict = Depends(decode_access_token)):
        if token_payload["vai_tro"] not in roles:
            raise HTTPException(status.HTTP_403_FORBIDDEN, "Không có quyền truy cập")
        return token_payload
    return _dep

# usage in a router
@router.post("/topics/{topic_id}/approve", dependencies=[Depends(require_role("BO_MON"))])
def approve_topic(topic_id: int, ...): ...
```
Source pattern: `research/STACK.md` "Custom RBAC via FastAPI Depends" row + `research/PITFALLS.md` Pitfall 9's "How to avoid" guidance — combined here into a concrete code skeleton.

### Pattern 2: Topic-registration concurrency — DB-enforced, not app-enforced

**What:** Two independent invariants from the locked ERD (§3.2.5, quoted verbatim — see Common Pitfalls) must both hold under concurrent requests: exactly one active topic per student, and exactly one student per topic.
**When to use:** UC1.2 (student registers an existing GV-proposed topic) — this is the phase's designated concurrency test target per CONTEXT.md `<specifics>`.
**Example (conditional UPDATE, from §3.2.5):**
```python
# backend/app/services/topics.py
result = db.execute(
    text("UPDATE de_tai SET sinh_vien_id = :sv, trang_thai = 'CHO_DUYET' "
         "WHERE id = :dt AND sinh_vien_id IS NULL"),
    {"sv": sinh_vien_id, "dt": de_tai_id},
)
db.commit()
if result.rowcount == 0:
    raise HTTPException(409, "Đề tài vừa được người khác đăng ký")
```
The `sinh_vien_id_dang_hoat_dong` generated column + `UNIQUE KEY` (verbatim SQL in Common Pitfalls) enforces the "1 SV : 1 active topic" side independently — MySQL permits multiple `NULL`s in a UNIQUE index, so only genuinely-conflicting rows collide.

### Pattern 3: httpOnly refresh cookie + in-memory access token, with axios 401-retry interceptor

**What:** Access token lives only in JS memory (a zustand store), never in `localStorage`/`sessionStorage`. Refresh token is a `Secure; HttpOnly; SameSite=Lax` cookie set by the login/refresh endpoint. On page reload, the access token is gone; the app calls `/api/auth/refresh` once at startup (browser auto-attaches the cookie) to re-mint it before rendering protected routes.
**When to use:** All authenticated screens (D-07).
**Trade-offs:** More secure against XSS (no token in JS-readable storage) than `localStorage`, at the cost of one extra round-trip on every page load — acceptable given NFR-12's 1-second budget is for data endpoints, not auth bootstrap.
**Example (cookie-setting, matches confirmed 2026 best practice — see Sources):**
```python
response.set_cookie(
    key="refresh_token", value=refresh_jwt,
    httponly=True, secure=True, samesite="lax",
    path="/api/auth",  # scope the cookie narrowly
    max_age=60 * 60 * 24 * 7,  # 7 days
)
```
`[CITED: multiple 2026 FastAPI-auth guides — see Sources; general pattern, not project-specific]`

### Anti-Patterns to Avoid
- **Checking role only in React (hiding buttons):** Server must independently reject with 403 — see Pitfall 9 and NFR-04's explicit test protocol (call the API directly with the wrong role/no ownership, expect 403 for every endpoint in the OpenAPI docs).
- **Check-then-act registration (`SELECT` then `UPDATE` in two statements):** Race-loses to a second concurrent request; must use the single conditional `UPDATE` (rowcount check) or `SELECT ... FOR UPDATE` inside one transaction (§3.2.5, quoted below).
- **Forwarding the user's JWT to the (future, Phase 4) AI service:** Not relevant to Phase 2's stub, but the interface should already be shaped so the real Phase 4 client uses a static API key, never the user's Bearer token (§3.3.8 decision, quoted below) — build the stub's function signature accordingly now.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Password hashing | Custom hash/salt scheme, or `passlib` wrapper | `bcrypt` called directly (`bcrypt.hashpw`/`checkpw`) | `passlib` is unmaintained since ~2020 and breaks with newer bcrypt/Python `[CITED: research/STACK.md]` |
| JWT encode/decode/expiry | Hand-rolled signing | `PyJWT` | FastAPI's own docs migrated off `python-jose`; PyJWT is actively maintained `[CITED: research/STACK.md]` |
| Concurrency-safe "first writer wins" | Application-level locking (e.g., Python `threading.Lock`, in-memory mutex) | MySQL row-level locking via conditional `UPDATE`/`SELECT...FOR UPDATE` inside a transaction | Application-level locks do not work across multiple uvicorn worker processes; DB-level locking is process-agnostic (§3.2.5) |
| Unicode text comparison | Manual diacritic-stripping/fuzzy matching | `unicodedata.normalize("NFC", text)` at every ingestion boundary (Pydantic validator) | Vietnamese NFC/NFD mismatches silently break exact-match queries and later semantic comparison (Pitfall 1) |
| SPA client-side routing fallback on Apache | Custom `mod_rewrite` regex rules | `FallbackResource /index.html` inside the client's `<Directory>` block | Simpler and specifically documented for this use case by Apache itself `[CITED: httpd.apache.org/docs/2.4/mod/mod_dir.html]` — only falls back when no other handler matches, so static assets (JS/CSS) still serve normally |

**Key insight:** Every "don't hand-roll" item above corresponds to a pitfall the project's own `research/PITFALLS.md` flags as high-recovery-cost if discovered late (RBAC/IDOR = HIGH cost; concurrency = the phase's own success criterion 4). None of these are optional polish — they are the load-bearing correctness guarantees of Phase 2.

## Common Pitfalls

### Pitfall 1: MySQL collation defaulting away from `utf8mb4_vietnamese_ci`

**What goes wrong:** If the database/table charset is left at server default or set to `utf8`/`utf8mb4_general_ci`, Vietnamese name/title sorting and comparison behave incorrectly, and seed data with the full diacritic range (ơ, ư, ê with stacked tones) may render as `?` or mangled bytes.
**Why it happens:** ORM-generated `CREATE TABLE` statements inherit the ORM/migration tool's default unless explicitly set; copy-pasted tutorial migrations often say `utf8` without `mb4`.
**How to avoid:** The design doc is explicit and must be followed verbatim — set collation at the **database** level (inherited by tables/columns), not per-column:
> `[VERIFIED: docs/chuong-3-thiet-ke/02-thiet-ke-csdl.md §3.2.1]` "**Bảng mã tiếng Việt:** mọi bảng và cột văn bản dùng `CHARACTER SET utf8mb4 COLLATE utf8mb4_vietnamese_ci` (đặt ở mức database, kế thừa xuống bảng/cột)"
**Warning signs:** `SHOW CREATE TABLE` for any table shows a collation other than `utf8mb4_vietnamese_ci`; sinh viên/giảng viên name lists sort in an order a Vietnamese speaker calls "wrong."
**Phase to address:** The very first Alembic migration (create-database/create-schema step), verified against seed data with the full diacritic range (NFR-13).

### Pitfall 2: NFC/NFD Unicode mismatch silently breaking exact-match and future semantic comparison

**What goes wrong:** Vietnamese text can arrive as precomposed (NFC) or decomposed (NFD) Unicode; two visually-identical strings compare as different, breaking `WHERE ten_de_tai = ?` lookups and (later, Phase 4) semantic-duplicate detection.
**How to avoid:** Design doc mandates normalization at every entry point:
> `[VERIFIED: docs/chuong-3-thiet-ke/02-thiet-ke-csdl.md §3.2.1]` "**Chuẩn hóa Unicode NFC:** mọi văn bản ... được chuẩn hóa **NFC** tại **mọi điểm nhập liệu** trước khi ghi vào CSDL"
Implement as a shared Pydantic `field_validator` (`unicodedata.normalize("NFC", v)`) applied to every text field (`ten_de_tai`, `ho_ten`, `mo_ta`, etc.) — one utility function, imported everywhere, not reimplemented per schema.
**Phase to address:** Phase 2 (D-06 already locks this) — write one unit test: two byte-different-but-visually-identical strings normalize to the same stored value.

### Pitfall 3: RBAC enforced only in the React UI (IDOR)

**What goes wrong:** Hiding buttons/menus per role in React while the corresponding FastAPI endpoint has no independent server-side check lets any authenticated user access data belonging to another role/user by calling the API directly (e.g., a SV account guessing another topic's ID).
**How to avoid:** Build the shared `require_role`+ownership dependency (Pattern 1) during the *first* router, not retrofitted. NFR-04's own verification method is explicit and should become a Phase 2 test:
> `[VERIFIED: docs/chuong-2-khao-sat-phan-tich/04-yeu-cau-phi-chuc-nang.md, NFR-04 row]` "Test gọi API trực tiếp (không qua UI) với JWT hợp lệ nhưng sai vai trò/không sở hữu dữ liệu, kỳ vọng HTTP 403 cho toàn bộ endpoint được liệt kê trong OpenAPI docs của Web API"
**Phase to address:** Phase 2, first UC (§3.2.5/Pitfall recovery cost is rated HIGH if discovered late — requires auditing every route).

### Pitfall 4: Apache reverse-proxy misconfiguration discovered only at deployment time

**What goes wrong:** Developing against `uvicorn localhost:8001` directly for weeks and adding Apache "at the end" means upload-size limits, proxy timeouts, `X-Forwarded-Proto`/`root_path` handling, and SPA-routing fallback are all untested until deployment — too late to fix comfortably.
**How to avoid:** D-11/D-12 already schedule Apache in week 1. Concretely configure, from day one:
- `uvicorn --proxy-headers` (trust `X-Forwarded-*` from Apache) so FastAPI generates correct `https://` links/redirects behind the proxy.
- `ProxyTimeout` ≥ 60s (D-12; matches NFR-15's ≥30s-plus-margin recommendation for the *future* Phase 4 AI document check, set now so it doesn't need revisiting).
- `LimitRequestBody` ≥ 20MB (D-12; Phase 2 has no file uploads yet, but the value must already be in place per the locked decision).
- `FallbackResource /index.html` for the React Router SPA (see Don't Hand-Roll) — without it, a browser refresh on any non-root route (e.g. `/topics/42`) returns Apache's 404, not the React app.
**Phase to address:** Phase 2, alongside the first working API endpoint — test through `https://localhost`, never only `http://localhost:8001` directly.

### Pitfall 5: Faker's `vi_VN` locale has an incomplete/buggy address provider

**What goes wrong:** `Faker('vi_VN').address()` in the currently-published version leaks an English placeholder token into otherwise-Vietnamese output.
**Verification (this session):**
```
$ Faker('vi_VN').address()
'435 John Tổ\nJohnXã, 191741'
```
`[VERIFIED: local venv test, faker 40.39.0 — "John" leaking into a Vietnamese address template is reproducible, not a one-off]`
**How to avoid:** Do not use `.address()` for seed data (`sinh_vien`/`giang_vien` tables have no address column per the verbatim ERD anyway — `lop`/`khoa`/`hoc_vi` are the only extra fields). `.name()` and `.phone_number()` were verified clean. If any future field needs an address-like string, write a small custom Faker provider instead of trusting `vi_VN`'s built-in one.
**Phase to address:** Phase 2 seed script (DATA-01) — spot-check every Faker method actually used against real Vietnamese output before trusting it in the idempotent seed script, not just the ones this research happened to check.

### Pitfall 6: JWT secret/config accidentally hardcoded or committed

**What goes wrong:** Under time pressure, a JWT signing secret gets hardcoded in `core/security.py` "for now" and is never moved to env config before the repo is shared/graded.
**How to avoid:** `pydantic-settings` `BaseSettings` reading from `.env` (gitignored) from the very first commit; NFR-03 explicitly tests for this:
> `[VERIFIED: docs/chuong-2-khao-sat-phan-tich/04-yeu-cau-phi-chuc-nang.md, NFR-03 row]` "JWT ký bằng secret key đọc từ biến môi trường (không hardcode trong mã nguồn)"
**Phase to address:** Phase 2, first commit of `core/config.py`.

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|-----------------------|
