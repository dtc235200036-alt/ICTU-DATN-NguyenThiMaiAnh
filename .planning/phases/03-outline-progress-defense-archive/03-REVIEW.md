## Summary

I reviewed the Phase 3 backend (outline, progress, defense, archive, notifications, dashboards, shared document upload and duplicate-check pipeline), migrations 0006 through 0009, the Phase 3 frontend features, and the deploy scripts and Apache config. As instructed, I left out `backend/app/services/ai_client.py`, the compose file and migration 0010, which plan 04-05 is still changing. I read the committed stub only to check the `ref_id` contract.

**What holds up:**
- Row-level authorization on reads and writes is consistent: `documents.can_view`, `_can_view_topic`, committee-member checks, and owner-scoped notification `UPDATE`s all check the caller.
- Stored paths are always generated by the server (`{loai}/{uuid}.{ext}`) and re-checked by `storage_path`.
- Magic-byte validation is enforced.
- Status changes use conditional `UPDATE`s, and notifications are committed in the same transaction as the change they announce.
- `LIKE` search uses `autoescape=True`.
- NFC normalization is applied at every text input path checked (NFCModel, upload filenames, extracted text, CSV cells, progress `noi_dung`, archive search).

No IDOR was found on downloads, scores, reports or notifications.

**Main concerns:**
1. One denial-of-service path any student can trigger: DOCX text extraction allows up to 150 MB of decompressed XML to be parsed in memory.
2. Several concurrency and state-machine gaps in UC4. One can make a defense permanently impossible to finalize. One lets `finalize` average a score from a lecturer who is no longer on the committee.
3. The shared check pipeline's `ref_id` is interpreted as a `tai_lieu_do_an` id, while the archive ingests `do_an_kho` ids.
4. Peer (unpublished) document passages are shown to students.
5. Several frontend screens show an empty state or an endless skeleton when a request fails.

## Critical Issues

### CR-01: DOCX extraction parses up to 150 MB of decompressed XML in the request thread, while holding the topic row lock (memory DoS by any student)

**File:** `backend/app/services/documents.py:34`, `backend/app/services/documents.py:101-108`, `backend/app/services/documents.py:172`, `backend/app/services/outlines.py:100,132`
**Issue:** `_MAX_DOCX_UNCOMPRESSED_BYTES = 150 MB` is the only guard before `Document(BytesIO(content))`. XML compresses at roughly 1000:1, so a DOCX of about 1 MB (well under the 20 MB limit) can hold a 150 MB `word/document.xml` made of millions of tiny `<w:p/>` elements.

lxml builds a full DOM for that. The memory cost is several times the XML size, which means gigabytes. It runs:
- synchronously inside `documents.store()`,
- inside the outline, final-report and progress submit transactions,
- while `SELECT … FOR UPDATE` holds the `de_tai` row.

The `api` service has no memory limit in compose and runs a single worker. Any logged-in student (outline, final report or progress attachment upload) can OOM-kill the API, or the host, which this machine has hit before.

Note: the declared `file_size` check itself is sound, because CPython's `ZipExtFile` caps output at the declared size. The problem is that the ceiling is far too high and the parse is not streamed.
**Fix:** Lower the ceiling and stream-parse `document.xml` instead of building a DOM. Move extraction out of the locked transaction.
```python
_MAX_DOCX_UNCOMPRESSED_BYTES = 25 * 1024 * 1024   # tổng giải nén
_MAX_DOCX_XML_BYTES = 15 * 1024 * 1024            # riêng word/document.xml

# extract_text (DOCX): stream thay vì python-docx DOM
from lxml import etree
W_NS = "{http://schemas.openxmlformats.org/wordprocessingml/2006/main}"
with zipfile.ZipFile(BytesIO(content)) as zf:
    info = zf.getinfo("word/document.xml")
    if info.file_size > _MAX_DOCX_XML_BYTES or sum(i.file_size for i in zf.infolist()) > _MAX_DOCX_UNCOMPRESSED_BYTES:
        return None
    paras, buf = [], []
    with zf.open(info) as fh:
        for event, el in etree.iterparse(fh, events=("end",), resolve_entities=False, huge_tree=False):
            if el.tag == W_NS + "t":
                buf.append(el.text or "")
            elif el.tag == W_NS + "p":
                paras.append("".join(buf)); buf.clear()
                el.clear()
    text = "\n".join(paras)
```
Also:
- Set `deploy.resources.limits.memory` (or `mem_limit`) on `api`.
- Consider running `extract_text` before `_get_topic_locked_or_404` (it only needs `vf.content`) and passing the result into `store()`, so the row lock is not held during parsing.

## Warnings

### WR-01: A committee can become permanently impossible to finalize (one member unavailable after partial scoring)

**File:** `backend/app/services/defense.py:332-339`, `backend/app/services/defense.py:994-996`, `backend/app/services/defense.py:1046-1060`
**Issue:** `finalize` requires `len(scores) == n_members`. If any lecturer in a committee is locked (`bi_khoa`), leaves, or cannot score, and any other member has already scored any student of that committee:
- `update_committee` returns 409 "Hội đồng đã có điểm", so the member cannot be replaced.
- `finalize` returns 409 "Chưa đủ thành viên chấm điểm".
- No endpoint deletes a score or overrides the quorum.

A locked lecturer also can no longer log in (`get_current_user` rejects `bi_khoa`), so they cannot score. The only way out is to edit the database by hand. On defense day this blocks UC4.4 and UC5.2 for every student in that committee.
**Fix:** Pick one of the following and cover it with a test:
- (a) Let Bộ môn replace a member who has no score rows. Refuse only when the member being removed has scores:
  ```python
  scored_by_removed = select(func.count()).select_from(DiemBaoVe).join(LichBaoVe).where(
      LichBaoVe.hoi_dong_id == hoi_dong_id, DiemBaoVe.giang_vien_id.in_(removed_gv_ids))
  ```
- (b) Add a Bộ môn "finalize with present members" override that records the reason.

### WR-02: A score from a member being removed can race with `update_committee`, and `finalize` then counts a non-member's score

**File:** `backend/app/services/defense.py:325-381`, `backend/app/services/defense.py:985-1022`, `backend/app/services/defense.py:1046-1062`
**Issue:**
- `update_committee` locks the `hoi_dong` row and checks `has_scores` with a plain read.
- `score()` locks only the `lich_bao_ve` row, and checks membership with a non-locking `_is_member` count.

These two locks never conflict. So lecturer X can pass `_is_member`, and `update_committee` (seeing zero scores) can remove X and add Y. Both commit. The result: `diem_bao_ve` holds X's score although X is not a member.

`finalize` then counts every `diem_bao_ve` row for the `lich` without joining `thanh_vien_hoi_dong`. Once the other members have scored, `len(scores) == n_members` is true even though Y never scored. The official `diem_trung_binh` is then computed from a non-member's score and archived.
**Fix:**
- In `score()`, take a shared lock on the committee row so it serializes with `update_committee`/`add_schedule`:
  ```python
  hd = db.execute(select(HoiDong).where(HoiDong.id == lich.hoi_dong_id).with_for_update(read=True)).scalar_one()
  ```
- In `finalize`, count only scores from current members:
  ```python
  scores = db.execute(
      select(DiemBaoVe.diem)
      .join(ThanhVienHoiDong, (ThanhVienHoiDong.giang_vien_id == DiemBaoVe.giang_vien_id)
            & (ThanhVienHoiDong.hoi_dong_id == lich.hoi_dong_id))
      .where(DiemBaoVe.lich_bao_ve_id == lich_id)
  ).scalars().all()
  ```

### WR-03: A student can resubmit the final report after being scheduled (race), and `add_schedule` skips topic eligibility checks

**File:** `backend/app/services/defense.py:147-163`, `backend/app/services/defense.py:717-780`
**Issue:** `submit_final_report` locks the `de_tai` row and checks "not yet scheduled" with a plain count. `add_schedule` locks the `hoi_dong` row, never locks `de_tai`, then inserts the `lich_bao_ve` row.

If the two run at the same time, the student commits a new `BAO_CAO_CUOI` version after being scheduled. That breaks the rule "once scheduled, no new version". It also changes which file the committee downloads and which file UC5.2 archives.

`add_schedule` also skips several checks:
- It does not check `topic.trang_thai == DA_PHAN_CONG`.
- It does not check that the outline is `DA_DUYET`.
- It does not check that `topic.sinh_vien_id` is set. The `NOT NULL` failure on `sinh_vien_id` is caught as `IntegrityError` and reported as the misleading "Sinh viên đã được xếp vào một hội đồng khác" (line 778-780).
**Fix:** In `add_schedule`, lock the topic (`select(DeTai)…with_for_update()`) after the committee lock, so it serializes with `submit_final_report`. Also check:
```python
if topic.trang_thai != DA_PHAN_CONG or topic.sinh_vien_id is None:
    raise HTTPException(409, _NOT_ASSIGNED_DETAIL)
```

### WR-04: Deleting a milestone or committee races with child inserts and returns an unhandled 500

**File:** `backend/app/services/progress.py:376-383`, `backend/app/services/progress.py:417-470`, `backend/app/services/defense.py:423-437`
**Issue:**
- `delete_milestone` locks the cohort and counts reports, but `submit_report` never locks the cohort or the `moc_tien_do` row. A report committed between the count and `db.delete(moc)` makes the DELETE fail on `fk_bao_cao_tien_do_moc`. That `IntegrityError` is not caught, so the client gets a 500.
- Likewise, `delete_committee` uses `db.get(HoiDong)` without `FOR UPDATE`, while `add_schedule` does lock it. A schedule added concurrently causes an FK failure and a 500.
**Fix:** Take locking reads on the parent row on both sides:
- `submit_report`: `select(MocTienDo).where(MocTienDo.id == moc_id).with_for_update(read=True)`
- `delete_milestone`: `with_for_update()` on the milestone
- `delete_committee`: `select(HoiDong)…with_for_update()`

Also wrap the delete commit in `except IntegrityError: rollback; raise HTTPException(409, …)`.

### WR-05: Background check `run` has no ownership token, so stale runs and rechecks corrupt `chi_tiet_trung_lap`

**File:** `backend/app/services/document_check.py:92-136`, `backend/app/services/document_check.py:148-167`, `backend/app/services/document_check.py:243-262`
**Issue:**
- A run that takes longer than `DOCUMENT_CHECK_TIMEOUT_SECONDS` is flipped to `LOI` by `expire_if_stale`. Its final guarded `UPDATE … WHERE trang_thai = DANG_KIEM_TRA` then matches 0 rows, but the `chi_tiet` rows it inserted are still committed. The record ends up `LOI` with details.
- If a GV clicks "Kiểm tra lại" while that stale run is still going, `request_recheck` flips the row back to `DANG_KIEM_TRA`. Both runs then delete and insert `chi_tiet` and both final UPDATEs match. The result is duplicated and interleaved detail rows plus a `ty_le_tong` from whichever run commits last.
**Fix:** Stamp each run and only write results if the stamp still matches:
- Pass the `thoi_diem` value that `request_recheck`/`create_pending` set into `run(ket_qua_id, started_at)`.
- Guard the final UPDATE with `.where(KetQuaKiemTraTrungLap.thoi_diem == started_at)`.
- Only commit the `chi_tiet` inserts if that UPDATE's `rowcount == 1`; otherwise roll back.

### WR-06: The document-check `ref_id` is read as a `tai_lieu_do_an.id`, but the archive ingests under `do_an_kho.id`

**File:** `backend/app/services/document_check.py:69-78`, `backend/app/services/document_check.py:114-117`, `backend/app/services/archive.py:91-95`, `backend/app/services/archive.py:98-110`
**Issue:**
- `_label_for(task_db, item["ref_id"])` resolves every match with `db.get(TaiLieuDoAn, ref_id)`.
- `check_document(doc.id, …)` sends a `tai_lieu_do_an.id` as the self-exclusion key.
- `archive.ingest_payload`/`run_ingest` index `("DOCUMENT", report text)` under `do_an_kho.id`.

With a real AI service, the index would therefore return `do_an_kho` ids. Each match would be labelled with whatever unrelated `tai_lieu_do_an` has the same numeric id, which attributes plagiarism to the wrong thesis. The self-exclusion would also silently drop an unrelated archive record.

Today this is hidden only because the stub builds its document corpus from `tai_lieu_do_an` and ignores ingests. The plan 04-05 notes already describe the namespace collision. This finding records that the Phase 3 consumer (`_label_for`, and the `ref_id` passed in `run`) must change together with it.
**Fix:**
- Carry the namespace in each result item (`loai: DOCUMENT|ARCHIVE`) and resolve it by namespace (`TaiLieuDoAn` vs `DoAnKho`).
- Keep `check_document`'s `ref_id` in the `DOCUMENT` namespace only.
- After 04-05/04-06 land, add a test where `tai_lieu_do_an.id == do_an_kho.id` for different theses.

### WR-07: Check details show students verbatim passages from peers' unpublished outlines and final reports

**File:** `backend/app/services/document_check.py:188-240`, `backend/app/routers/documents.py:22-33`, `frontend/src/features/documents/routes.tsx` (route open to SINH_VIEN)
**Issue:** `GET /api/documents/{id}/check` returns `chi_tiet[].doan_trung` (the matched paragraph from the other document) and `do_an_trung` topic labels. A student can call this for their own submission. In the committed pipeline, the corpus is the latest `DE_CUONG`/`BAO_CAO_CUOI` of every current topic, not only the archive.

A student can therefore upload a document built from generic paragraphs and read back peers' in-progress outline or report text through repeated submissions (each resubmission is allowed while `YEU_CAU_SUA`, and progress attachments are unlimited). PI 3.4 needs matched passages shown to reviewers. It does not require exposing unpublished peer text to students.
**Fix:** In `detail()`, take the caller and redact `doan_trung` for `SINH_VIEN` when the source is not an archived (`do_an_kho`) thesis. Alternatively, limit the check corpus to archived theses plus previous cohorts (the 04-06 direction), and assert that in a test.

### WR-08: CSV import crashes with a 500 on malformed input, and the commit is unguarded

**File:** `backend/app/services/archive.py:388-407`, `backend/app/services/archive.py:485-486`
**Issue:**
- `csv.DictReader` iteration can raise `_csv.Error`. For example, any cell longer than the default `field_size_limit` (131072 chars) is easy to hit within the 2 MB allowance, and malformed quoting in strict dialects can also trigger it. The exception is not caught, so the whole import fails with an opaque 500 instead of the documented per-row E1 errors.
- The final `db.add_all`/`db.commit()` has no `IntegrityError`/`DataError` handling. Any constraint the pre-validation misses (e.g. a length difference under `utf8mb4_vietnamese_ci`, or a concurrent duplicate import) also gives a 500.
**Fix:**
```python
try:
    for raw in reader:
        ...
except csv.Error as exc:
    raise HTTPException(422, f"File CSV không hợp lệ ở dòng {reader.line_num}: {exc}") from None
...
try:
    db.add_all(new_rows); db.commit()
except (IntegrityError, DataError):
    db.rollback()
    raise HTTPException(409, "Không lưu được dữ liệu import — vui lòng kiểm tra lại file") from None
```
Also consider a DB-level unique index on `(khoa, ten_de_tai)` so the duplicate rule survives concurrent imports.

### WR-09: Editing a system-archived (`HE_THONG`) record overwrites the finalized defense score and unlinks the student

**File:** `backend/app/services/archive.py:289-299`, `backend/app/services/archive.py:312-317`
**Issue:** `update_record` applies `_apply()` to every record. For `nguon == HE_THONG`:
- `kho.diem = payload.diem` silently diverges from the locked `lich_bao_ve.diem_trung_binh`. The finalize step is described as one-way, but Bộ môn can rewrite the archived grade.

**Fix:** For `HE_THONG` records, make `diem`, `sinh_vien_id`, `ma_so_sinh_vien` and `ho_ten_sinh_vien` read-only on the server. Either reject a changed value with 422, or skip those fields in `_apply` when `kho.nguon == HE_THONG`.

**File:** `backend/app/services/documents.py:55-60`, `backend/app/services/documents.py:74-75`

### IN-05: Object URL revoked synchronously after `click()`
